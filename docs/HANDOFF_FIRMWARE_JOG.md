# ファームウェア担当エージェントへのハンドオフ（2）— シリアルからの速度ジョグと非アラーム停止

作成日: 2026-10-24
対象: `CoreXY_UFO`（M5Stack Core2 ファームウェア）リポジトリを担当するエージェント
送り元: `CoreXY_UFO_Game`（https://github.com/fooping-tech/CoreXY_UFO_Game）
前提資料: [HANDOFF_FIRMWARE.md](HANDOFF_FIRMWARE.md)（前回の依頼。§4.1 ホストウォッチドッグ、§4.2 Z 専用コマンド、§4.3 移動中の位置通知）、[firmware_protocol.md](firmware_protocol.md)（現行プロトコルの調査メモ）
調査したファームウェア: `../CoreXY_UFO` HEAD `160742d`

## 1. 依頼の要点

ゲームから**キーを押している間だけクレーンが動き、離すと減速して止まる**操作（ジョグ）をしたい。現在のシリアルコマンドではこれができないため、次の 2 つを追加してほしい。

1. **シリアルからの速度ジョグ** `JOG`。一定間隔で送り続けている間だけ動き、途絶えたら減速停止する（デッドマン方式）。HOMED を保ち、ソフトリミットを守る。
2. **アラームにしない停止** `STOP`。実行中の XY 移動やジョグを減速して止める。HOMED は解除しない。

あわせて、既存のジョイスティックのジョグにある次の制約を、**ジョイスティック・シリアルの両方から撤廃**してほしい（§3.0）。

- テストモードが必須
- XY を動かすと HOMED が解除される
- ソフトリミットを見ていない（ホームの反対側にはリミットスイッチもない）
- シリアルからコマンドが来るとジョグが終わる

既存のジョイスティックのジョグ（`runJogSession`）が速度ジョグと減速停止をすでにしているので、それを土台にすれば実装量は抑えられるはずである。

## 2. 現状（ソースで確認した事実）

| 項目 | 現状 | 出典 |
|---|---|---|

| 移動を途中で止める手段 | `ABORT` だけ。即時停止し、**アラームを立てて HOMED を解除**する（`stopForAbort`）。復帰に `ALARM_CLEAR` → `HOME` が必要 | `MotionTask.cpp:150-159` |
| 相対移動 | `TEST_JOG` は `TEST_MODE ON` 中のみ、最大 50 mm、**HOMED を解除**する | `MotionTask.cpp:1004-`, `PlotterConfig.h:210-212` |
| 速度ジョグの仕組み | ジョイスティック（ESP-NOW）用の `runJogSession` がある。XY は `stepper_backend.setVelocityAB()` の速度モード（加減速 `JOY_ACCEL_MM_S2` = 600 mm/s²）。Z/アームは `sts_servo_bus` の速度ジョグ。リンクが `JOY_LINK_TIMEOUT_MS` = 250 ms 途絶えると終了し、`stopVelocity()` で**減速停止**する。ホーム側リミットに向かう速度は打ち消す | `MotionTask.cpp:1093-1250`, `JoystickMapping.cpp`, `PlotterConfig.h:225-245` |

| 移動中の位置 | `POS` には移動完了後にしか応答しない。ジョグ中は `updateMachinePositionEstimateFromBackend()` で内部の位置は更新している | `firmware_protocol.md` §2, `MotionTask.cpp:1196` |
| ログキュー | 24 行、満杯時は**黙って捨てる** | `main.cpp:34-43`, `TaskConfig.h:18` |

結論として、「押している間動き、離したら止まる」ことは `XY` の連続送信では作れない。小さな `XY` を連続で送ると、キーを離しても送信済みのぶんは止められない（`ABORT` 以外に手段がない）。

## 3. 要望

### 3.0 既存ジョグの制約を撤廃する（ジョイスティックとシリアル共通、優先度 高）

§2 の (a)〜(d) の制約は、**ジョイスティックのジョグと、新しいシリアルの `JOG` の両方から撤廃してほしい**。

| 制約 | 撤廃後の動作 |
|---|---|
| (a) `TEST_MODE ON` が必須 | XY ジョグも Z/アームのサーボジョグも **`TEST_MODE OFF` のままで動く**。テストモードが担っていた安全上の役割（サーボの保持チェックなど）がある場合は、それをジョグの開始処理に組み込むなどの代わりの仕組みを提案してほしい（§7） |
| (b) XY を動かすと HOMED を解除 | HOMED の状態で始めたジョグでは **HOMED を保つ**。位置は `updateMachinePositionEstimateFromBackend()` の推定（ステップ数から計算）を正とする。HOMED でない状態のジョグは現行どおり HOMED=NO のまま |
| (c) ソフトリミットを見ていない | HOMED の間は、ジョグ中も **X 0..390 / Y 0..200 の手前で減速して止まる**。境界までの残り距離を d、加速度を a とし、その軸の外向きの速度を `sqrt(2·a·d)` 以下に抑える。境界に着いたら外向きの速度だけ 0 にし、内向きには動ける。ホーム側のリミットスイッチの処理（`joyMaskTowardLimits` と即時停止）はそのまま残す |
| (d) シリアルからコマンドが来るとジョグが終わる | **ジョグは終わらせない**。ジョグ中のコマンドは次のように扱う（下の表） |

ジョグ中に届いたシリアルコマンドの扱い:

| 種類 | 例 | ジョグ中の動作 |
|---|---|---|
| 読み取り | `POS`、`M114`、`SERVO_STATUS`、`HOME_STATUS`、`LIMIT_STATUS`、`TMC_STATUS`、`JOB_STATUS`、`CONFIG`、`HELP` | **ジョグを続けたまま、その場で応答する**。`POS` はジョグ中の現在位置（推定値）と `MOTION=YES` を返す |
| ジョグの更新 | `JOG ...` | セッションの速度を更新する（§3.1） |
| 停止 | `STOP`、`ABORT` | `STOP` は減速停止（§3.2）、`ABORT` は即時停止・アラーム（現行どおり） |
| 移動・設定の変更 | `XY`、`G0`/`G1`、`HOME`、`SERVO_TURN`、`SERVO_ANGLE`、`TEST_JOG`、`JOB_*`、`TEST_MODE` など | **ジョグを止めずに拒否する**: `NACK_<CMD> reason=jog_active`（`XY` なら `NACK_XY ... reason=jog_active`）。順番待ちにはしない。ジョグが終わったあとで古い移動が勝手に始まるのを防ぐため。ホストは `STOP` か `JOG 0 0` で止めてから送り直す |

ジョイスティックのジョグでも、この表のとおりに動くようにしてほしい（PC から `POS` で位置を見ながらジョイスティックで操作できる）。

### 3.1 `JOG` — シリアルからの速度ジョグ（優先度 高）

```
JOG <vx_mm_s> <vy_mm_s> [<z_counts_s> <arm_counts_s>]
```

- `runJogSession` と同じ経路で動かす（`JogRequest` を作って `jog_queue` に入れる、またはセッションに直接渡す）。ジョイスティックとシリアルのどちらが入力元でも同じセッションの仕組みを使う想定。
- **デッドマン:** 最後の `JOG` から `JOG_TIMEOUT_MS`（既定 250 ms、`JOY_LINK_TIMEOUT_MS` と同じ）以内に次の `JOG` が来なければ、減速停止してセッションを終える。ホストは押している間 50 ms（20 Hz）ごとに送り続ける。
- `JOG 0 0`（すべて 0）を受けたら減速停止する。キーを離したときに送る。
- セッション中のコマンドの扱い、HOMED の保持、ソフトリミット、`TEST_MODE` 不要は §3.0 のとおり。
- **HOMED でない場合:** シリアルからの XY ジョグは `NACK_JOG reason=not_homed` で拒否する（ゲーム側は先に `HOME` する）。Z/アームのジョグは許可してよい。ジョイスティックは HOMED でなくても現行どおりジョグしてよい（復旧操作に使うため）。
- 速度の上限: |v| は `MAX_FEED_MM_MIN` / 60 で切る。加減速はシリアルのジョグ用に `SERIAL_JOG_ACCEL_MM_S2` を設けてほしい（既定 600、ジョイスティックと同じでよい）。
- 拒否する条件: アラーム中、ホーミング中、ジョブ実行中（`pollJoystick` の判定と同じ）。

**応答（ログキューを溢れさせないこと）:** 20 Hz で送られる `JOG` に毎回 `ACK QUEUED` を返すと、24 行のログキューがすぐ溢れて他の行（`ACK_XY` など）が捨てられる。
- セッション開始時に 1 回: `JOG start vx=.. vy=.. z=.. arm=..`
- 継続中の `JOG` には何も返さない（または、溢れない頻度に限った応答）
- 終了時に 1 回: `JOG end reason=<idle|zero|timeout|command|abort|alarm|limit_x|limit_y|soft_limit> X=.. Y=.. HOMED=YES|NO`
- 拒否: `NACK_JOG reason=<not_homed|alarm|homing|job_active|busy|bad_args>`（`busy` = `XY` などの移動を実行中。その移動が終わるか `STOP` してから送る）

### 3.2 `STOP` — アラームにしない減速停止（優先度 高）

```
STOP
```

- 実行中の `XY` 移動・ジョグ・ジョブを**減速して**止める。キューに積まれている移動コマンドは破棄する。
- **アラームにせず、HOMED も解除しない。** 停止後の位置は計画どおりなら既知なので、そのまま次の `XY` を受け付けてほしい。
- 応答: `STOP complete X=.. Y=.. HOMED=YES|NO`。止められた `XY` には `NACK_XY ... reason=stopped` を出す（`abort` と区別したい）。
- `ABORT`（即時停止・アラーム・HOMED 解除）は非常停止としてそのまま残す。ゲームは「ユーザーの操作による停止」に `STOP`、「非常停止」に `ABORT` を使い分ける。
- `STOP` はキュー待ちを経由せず即時に効くこと（`ABORT` と同じ扱い）。移動中に送ってもすぐ反応しないと意味がない。

### 3.3 ジョグ中の位置通知（優先度 中、前回 §4.3 の一部）

ジョグ中はゲーム側が位置を推定できない（目標位置がない）。少なくともジョグ中は 20 Hz 程度で 1 行の位置を出してほしい。

```
JOG_POS X=.. Y=.. VX=.. VY=.. Z_ABS=.. ARM_ABS=..
```

- ログキューの取りこぼしに強いよう 1 行に収める。取りこぼしがあっても次の行で補えるので、捨てられても問題にはならない。
- 前回依頼した `REPORT ON <ms>`（移動中の定期通知）を実装する場合は、それに統合してよい。

## 5. ゲーム側の対応予定（ファームウェア対応後）

- バックエンドに `jog {vx, vy}` と `soft_stop` を追加する。`jog` はモーションロックの外で扱い、Godot は矢印キーを押している間 20 Hz で送る（デッドマン）。キーを離したら `jog {0, 0}`。
- これは「モーションコマンドを自動で再送しない」というゲーム側の原則の例外になる。ジョグのリフレッシュは「生きている」ことの通知で、途絶えればファームウェアが止める仕組みなので、安全側に倒れる。
- Space キーは今は Mock しか止めていない。対応後は WebSocket 接続中でも実機に `stop`（`ABORT`）を送るように直す。ゲーム中の通常の停止は `STOP` を使う。
- ジョグ中の位置は `JOG_POS` を `measured:true` として扱う。
- 解析は `backend/src/corexy_ufo_backend/serial_service/protocol.py`、実機を模したテストは `backend/tests/conftest.py` の `FakeFirmware` を更新する。応答形式を決めたら行の例を `docs/firmware_protocol.md` の書式で教えてほしい。

## 6. 互換性の約束（前回 §5 と同じ）

- 既存の行の先頭トークン（`ACK QUEUED`、`ACK_XY`、`NACK_XY`、`HOME complete`、`POS `、`SERVO_TURN id=`、`ABORT complete`、`ALARM_CLEAR complete`、`TEST_MODE result=`）は変えないこと。フィールドの追加は問題ない。
- 新しい行は「先頭トークンで種類が決まる」形にしてほしい（`JOG start`、`JOG end`、`NACK_JOG`、`JOG_POS`、`STOP complete`）。

## 7. 判断を仰ぎたい点

1. HOMED のまま速度ジョグをしてよいか（ステップ数からの位置推定を信用してよいか）。脱調の心配があるなら、ジョグの最高速度を下げる・電流を上げるなどの条件を教えてほしい。
2. `STOP` で減速停止したあとの位置は、計画上の位置で正確か。`XY` の途中で止めたときに、プランナーのキューと実位置がずれないか。
3. `TEST_MODE` が担っていた安全上の役割（サーボのトルク・保持チェック、ジョイスティックを本番で使わない前提 `PlotterConfig.h:219` など）。撤廃は決定事項なので、必要な確認はジョグ開始時の処理などに移す方法を提案してほしい。
4. ジョグ中に読み取り系コマンドへ即答するには、コマンドを motionTask の外（commandTask 側）で処理するか、ジョグのループ内で処理する必要がある。どちらの構成にするかと、`POS` の値（推定位置）を他タスクから読むときの排他の扱い。
5. ジョイスティックとシリアルの `JOG` が同時に来た場合の優先順位（提案: シリアル優先。ジョイスティックの入力はシリアルのジョグ中は無視する）。
