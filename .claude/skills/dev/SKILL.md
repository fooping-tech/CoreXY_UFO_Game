# /dev — GitHub 開発ワークフロー

ユーザーは GitHub の操作に慣れていない。操作方法を一つずつ質問せず、**GitHub の状態を調べて自分で判断して進める**。
確認するのは次の 3 つだけ: 仕様の重要な曖昧さ、破壊的な操作、マージ。

コードの設計制約とテスト手順はプロジェクト専用スキル **`corexy-ufo-game`** にある。実装（フェーズ 2・4・8）ではそちらを必ず読む。このスキルは GitHub まわりの手順だけを扱う。

## 0. 毎回最初にやること — 状態の復元

GitHub が作業状態の唯一の情報源。会話の記憶より GitHub を信じる。何をするにも、まず次を実行する。

```bash
python3 .claude/skills/dev/scripts/dev_state.py            # 今のブランチの Issue（なければ status）
python3 .claude/skills/dev/scripts/dev_state.py issue 12   # Issue #12 の状態と次のフェーズ
python3 .claude/skills/dev/scripts/dev_state.py pr 15      # PR #15 から逆引き
python3 .claude/skills/dev/scripts/dev_state.py status     # 開いている Issue / PR の一覧
python3 .claude/skills/dev/scripts/dev_state.py next       # 誰も着手していない Issue の候補
```

出力の `NEXT phase N` が次にやるフェーズ。**完了済みのフェーズは繰り返さない**（ブランチ・PR を二重に作らない）。`⚠` の警告（PR やブランチが複数ある）はユーザーに伝えてから進める。`--json` で詳細（未解決のレビュー指摘の URL など）も取れる。

## 1. 指示と動き方

| ユーザーの指示 | やること |
|---|---|
| 「次に対応するIssueを選んで」 | `dev_state.py next` → 上位 1〜3 件を理由付きで提案する。着手はユーザーが選んでから |
| 「Issue #12を実装して」 | `issue 12` で状態を確認 → 次のフェーズから **6（PR 作成）まで**進める。マージはしない |
| 「PRまで作って」 | 対象の Issue（今のブランチか、直前の話題）でフェーズ 6 まで |
| 「PR #15のレビューに対応して」 | `pr 15` → フェーズ 7→8（指摘を重要度別に整理して修正 → 再検証 → push → 返信）→ 7 |
| 「今の開発状況を教えて」 | `status`、必要なら開いている PR ごとに `pr N`。専門用語を避けて要約する |
| 「マージできる状態？」 | `pr N` / `issue N` → フェーズ 9 の判定基準（§3）を一つずつ答える。マージはしない |
| 「このPRをマージして」 | §3 の基準を満たしていれば、その指示を承認としてフェーズ 9 → 10。満たしていなければ理由を説明して止まる |
| 「さっきの作業の続きをやって」 | 引数なしの `dev_state.py`（今のブランチから推定）→ `NEXT` のフェーズから再開。分からなければ `status` で候補を示す |
| 「Issueを作って」「これをIssueにして」 | 受け入れ条件付きの Issue を作る（[phases.md](references/phases.md) §1） |

対象が曖昧なとき（Issue 番号がなく、ブランチからも分からない）は `status` の結果を見せて 1 回だけ聞く。

## 2. フェーズ（それぞれ単独で実行・再開できる）

詳しい手順とコマンドは [references/phases.md](references/phases.md)。各フェーズの最初に「もう済んでいないか」を確認する。

| # | フェーズ | 済んでいるかの確認 | 要点 |
|---|---|---|---|
| 1 | Issue の取得と要件整理 | — | `gh issue view N`。受け入れ条件を箇条書きにする。なければ作り、曖昧な点はユーザーに確認 |
| 2 | 調査 | — | `corexy-ufo-game` スキルの表で触るファイルを決める。実機が必要な変更かを判定する |
| 3 | ブランチ作成 | `dev_state` に branch がある | `種類/<Issue番号>-<内容>`（例 `feat/12-keyboard-jog`）を最新の `origin/main` から作る |
| 4 | 実装とテスト | — | 変更は Issue の範囲だけ。`tools/verify.sh` を通す。テストを足す |
| 5 | コミットと push | 未 push が 0 | 意味のある単位でコミット。`git push -u origin <branch>` |
| 6 | PR 作成 | PR がある | テンプレートに沿って本文を書き、`Closes #N` を入れる。base は `main` |
| 7 | CI とレビューの確認 | — | `gh pr checks N --watch`、未解決のレビュー指摘（Codex の自動レビューを含む）を確認 |
| 8 | 修正と再検証 | 失敗・指摘が 0 | 指摘を重要度別に整理して対応 → verify → push → 指摘に返信して解決済みにする |
| 9 | マージ | PR が MERGED | **ユーザーの明示的な承認が必要**。`gh pr merge N --merge` |
| 10 | Issue クローズと報告 | Issue が CLOSED | Issue が閉じたかを確認し、結果をユーザーに報告する |

「Issue #12 を実装して」のような依頼では、フェーズ 1→6 を止まらずに進め、PR の URL と §5 の形式で報告して終える。

## 3. マージしてよい条件（フェーズ 9）

全部を満たすときだけ。一つでも欠けたら、マージせずに理由と次の手を説明する。

1. ユーザーが**この会話で、この PR について**マージを明示的に指示・承認した（以前の承認は引き継がない）
2. CI がすべて成功（`checks: success`）。CI がない・実行中なら待つか、理由を説明する
3. 未解決のレビュー指摘が 0、`CHANGES_REQUESTED` でない。**outdated（行が変わっただけ）の指摘も未解決として数える**。対応済みなら返信して解決済みにしてから数え直す
4. `mergeable: MERGEABLE`（`UNKNOWN` は計算中なので待つ）、base が `main`、手元のブランチがリモートより古くない
5. PR 本文に `Closes #N`、テスト結果、未解決事項がある
6. 実機が必要な変更（`corexy-ufo-game` スキル §5）なら、「実機未検証」であることをユーザーが承知している

## 4. 運用ルール（必ず守る）

- **main に直接 push しない。** 必ずブランチ → PR。フック `.claude/hooks/guard_git.py` が main への push、force push、`reset --hard` などの破壊的な操作、秘密情報を含むコミット、`gh api` による参照の書き換えを止める（`sh -c` やサブシェルの中も見る）。止められたら回避しようとせず、理由をユーザーに説明する。フックは補助で、main を実際に守るのは GitHub のブランチ保護。
- **1 Issue = 1 PR。** 既存のブランチ・PR があればそれを使う（`dev_state.py` の結果に従う）。
- Issue 番号を**ブランチ名と PR 本文**の両方に入れる（`Closes #N`）。
- PR の base は `main`。別の PR のブランチに積み重ねない（必要なら先の PR のマージを待つ）。
- PR 本文には変更概要、テスト結果、確認方法、未解決事項（実機未検証を含む）を書く。
- push のたびに CI の結果を確認し、失敗を残したまま報告を終えない。
- force push、履歴の書き換え、ブランチ削除、Issue・PR を閉じる操作は原則しない。必要なときはユーザーに確認する。
- 認証情報・秘密鍵・トークン・`.env` をコミットしない。
- コミットの末尾には、システムが指定する Co-Authored-By 行を付ける。PR 本文の末尾にも、指定された署名行を付ける。
- 同じ操作をやり直すときは、必ず状態を確認してからにする（冪等性）。例: PR 作成前に既存の PR を探す。コメントを重複して投稿しない。

## 5. ユーザーへの報告の仕方

GitHub に不慣れな人向けに、**何が終わり、何が残っていて、次にユーザーが何をすればよいか**を書く。

- 最初の 1 行で結論（例: 「PR #15 を作りました。CI は成功、マージにはあなたの承認が必要です」）
- Issue・PR は番号と URL を載せる
- テスト結果は件数で書く。実行していないもの（実機など）は「未検証」と書く
- 最後に、次にユーザーが言えばよい一言を示す（例: 「マージしてよければ『マージして』と伝えてください」）

## 6. 他のスキルとの分担

| 場面 | 使うもの |
|---|---|

| 検証の実行 | `tools/verify.sh`（CI と同じ内容） |
